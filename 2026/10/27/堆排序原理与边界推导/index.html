为什么堆排序要从 `n/2 - 1` 开始建堆？

发表于2026-10-27|更新于2026-10-27|算法学习
|总字数:4k|阅读时长:14分钟|浏览量:

为什么堆排序要从 n/2 - 1 开始建堆？

从一个容易被背下来的公式出发，把堆排序的复杂度、代码骨架、0 基与 1 基的边界差异，以及它和 PriorityQueue 的真实关系一次讲清。

引言

「手写一遍堆排序」是后端面试里的常客，而绝大多数人卡在同一个位置：建堆那行循环，起点为什么是 n/2 - 1？

把它背下来并不难，难的是说清它从哪来、为什么不能写成 n/2、以及当教材用 1 基数组而实际代码用 0 基数组时，哪些下标要跟着变。这三个问题一旦想通，堆排序就不再是一个需要记忆的算法，而是完全二叉树的下标算术 + 一次原地置换。

本文按这个顺序展开：先看堆排序在做什么，再推复杂度和建堆起点，然后逐处对齐 0 基与 1 基的边界，最后澄清一个高频误解——PriorityQueue 用了堆，但它不是堆排序。

一、堆排序只做两件事

堆排序的全部工作量可以压缩成两个阶段，理解了这个骨架，后面的公式都是它的推论。

  1. 建堆：把无序数组原地调整成一个大顶堆（或小顶堆）。
  2. 反复取堆顶：把堆顶（最大值）和当前末尾交换，最大值就归位到数组尾部；然后把有效范围缩短一格，重新调整堆顶。

关键洞察
阶段一结束后，堆顶永远是剩余元素里的最大值。每次交换都让一个元素彻底归位，代价是要让”外来的”堆顶重新下沉一次。

用大顶堆得到的是升序结果——这个方向容易记反，理由很直白：最大值被反复放到数组末尾，所以小的先留下、大的后到位。要降序就改用小顶堆，把所有比较符号反过来。

二、时间复杂度：为什么建堆是 O(n)，不是 O(n log n)

阶段 时间复杂度 说明
建堆（heapify） O(n) 从最后一个非叶子节点向前调整
每次取堆顶并下沉 O(log n)，共 n−1 次 堆顶与末尾交换后向下调整
总计 O(n log n) 最好、最坏、平均都是 O(n log n)

建堆是 O(n) 这一步反直觉，因为”对 n/2 个节点各做一次 O(log n) 调整”看起来应该是 O(n log n)。错在哪：绝大多数节点在树的最底层，它们的下沉距离几乎是 0。

按层求和就能看清。设根在第 0 层、树高为 h，第 h 层的节点数约为 n / 2^(h+1)，每个节点最多下沉 h 步：

这是一个级数，不是乘法。 下沉距离越长，节点数越少，两者相乘后整体收敛。

另外三个必须记住的属性

  • **空间 O(1)**：原地排序，只要下沉用循环而不是递归。
  • 不稳定：堆顶与末尾的交换会把相同元素的相对顺序打乱。
  • 最坏仍是 O(n log n)：不受输入分布影响，这是堆排序相对快排最大的优势——快排最坏会退化到 O(n²)。

与主流排序对照

排序 平均 最坏 空间 稳定性
堆排序 O(n log n) O(n log n) O(1) 不稳定
快速排序 O(n log n) O(n²) O(log n) 不稳定
归并排序 O(n log n) O(n log n) O(n) 稳定

三、手写实现：0 基原地版

五处值得停下来看的细节

  • 建堆从 n / 2 - 1 递减到 0，方向必须是从后往前——理由见第四节。
  • 排序阶段传给 siftDown 的 size 是开区间上界（也就是长度），每轮减一，已经归位的末尾元素不再参与比较。这是原地排序得以正确的核心：堆的”有效部分”和”已排序部分”共用同一个数组。
  • 下沉用 while 循环而不是递归，这样空间才能守住 O(1)。递归版本虽然更短，但会额外吃掉 O(log n) 栈帧。
  • largest == i 就 break，这是提前终止：一旦当前节点已不比孩子小，它不会再往下走。
  • n <= 1 直接返回，空数组和单元素天然有序，不需要特殊分支。

用 PriorityQueue 的简化写法（非原地）

时间 O(n log n)、空间 O(n)。代码短、不容易写错边界，但多花了线性额外空间，所以它只是堆排序思想的借用，不是堆排序本身。手写题推荐上一节的原地版本。

四、建堆起点 n/2 - 1 的推导

结论先行

n/2 - 1 是最后一个非叶子节点的下标（这里的 n/2 是整数除法）。

叶子节点天然满足堆性质，因此不需要调整；而从后往前处理，保证了每次调用 siftDown(i) 时它的两棵子树已经是堆。

推导：从”什么是叶子”反解

0 基完全二叉树中，节点 i 的左孩子是 2i + 1。节点是叶子 当且仅当它没有左孩子：

所以需要调整的下标范围是 [0, n/2 - 1]，起点取最大值 n/2 - 1。

还有第二条更直观的路：**最后一个节点是 n - 1，它的父节点是 (n-1-1)/2 = n/2 - 1**——完全二叉树里最后一个节点的父节点，必然是最靠右、也因此最靠后的那个非叶子节点。两种推导殊途同归。

一个高频混淆：2i+1、2i+2、n/2-1 各说各的事

式子 已知什么，求什么
2i + 1 已知父节点 i，求左孩子下标
2i + 2 已知父节点 i，求右孩子下标
n/2 - 1 已知数组长度 n，求最后一个非叶子父节点下标

前两个是「父 → 子」，最后一个是「长度 → 起点」。**”最后一个非叶子节点”本身就是父节点，不是它的孩子**，所以这里根本不存在”要不要写成 2i+1“的问题；最后一个非叶子父节点只有一个，唯一确定。

为什么必须从后往前

siftDown(i) 的正确性有一个前提：i 的左右子树已经是合法的堆——它只做”我和孩子比，谁大谁上来”的局部决策，无法修复子树内部的破坏。

从 n/2 - 1 递减到 0 时，处理 i 的那一刻，所有下标大于 i 的节点都已处理完毕，而孩子下标恒大于父节点下标，子树必然已成堆。反过来若从 0 往后建堆，孩子还没调整过，父节点比出来的结果下一轮就作废了。

边界验证（n = 8）

非叶子节点是 0, 1, 2, 3，最后一个是 **3 = 8/2 - 1**；再看节点 4，它的左孩子 2×4+1 = 9 ≥ 8，确实是叶子。建堆顺序即 3 → 2 → 1 → 0。

n n/2 - 1 说明
1 -1 循环一次都不执行，天然正确
2 0 唯一非叶子就是根
3 0 根有孩子 1、2
4 1 节点 1 是最后非叶子（孩子 3）
8 3 节点 3 是最后非叶子（孩子 7）

n = 1 时起点算出 -1 是正确行为，不是 Bug——它让建堆循环自然跳过。这就是为什么代码里 i >= 0 的判据要写成 >= 0 而不是 > 0。

五、0 基与 1 基：一套公式只能配套使用

很多教材用 1 基数组，因为下标算术更漂亮（孩子就是 2i，父就是 i/2）；而 Java、C 的真实数组是 0 基。两者的每个公式都要整体平移，混用必错。

核心公式对照

项目 0 基（0 ~ n-1） 1 基（1 ~ n）
左孩子 2i + 1 2i
右孩子 2i + 2 2i + 1
父节点 (i - 1) / 2 i / 2
最后一个非叶子 n/2 - 1 n/2
第一个叶子 n/2 n/2 + 1
建堆起点 n/2 - 1，递减到 0 n/2，递减到 1
排序交换 swap(0, end)，end 从 n-1 到 1 swap(1, end)，end 从 n 到 2
调整范围语义 [0, size)，size 是有效长度 [1, size]，size 是有效最大下标

0 基：

1 基：

三处最容易踩的边界

  1. 建堆起点差一位。 0 基是 n/2-1 配 i>=0；1 基是 n/2 配 i>=1。1 基写成 n/2-1 会漏掉最后一个非叶子节点，是有害错误；0 基写成 n/2 只是多调整了一个叶子，无害但多余。 这一正一反值得留意：同一个”差一位”，在不同基下严重程度完全不同。
  2. 排序循环的终止条件。 0 基 end > 0，1 基 end > 1。两者语义一致：剩最后一个元素时就停下，因为单元素天然有序，再多交换一次反而会把顺序弄乱。
  3. siftDown 的 size 语义。 0 基传长度（开区间），1 基传最大下标（闭区间）。把两边的传参方式搞混，要么数组越界，要么漏掉一个元素没参与比较。**建议在方法注释里写死”size 是长度还是最大下标”**，这是堆排序代码里最典型的隐性 Bug 来源。

完整对照示例（n = 8）

0 基 1 基
下标范围 0..7 1..8
非叶子节点 0,1,2,3 1,2,3,4
最后非叶子 3 = 8/2 - 1 4 = 8/2
建堆顺序 3,2,1,0 4,3,2,1
排序 end 取值 7,6,...,1 8,7,...,2

两者的非叶子节点个数都是 4，只是下标整体平移了 1。 这句话可以用来快速自检：如果你的实现算出的非叶子数量和 ⌊n/2⌋ 不一致，那一定是边界写错了。

实际工程里 Java 数组从 0 开始，优先写 0 基版本；1 基主要出现在教材伪代码和树状数组、线段树那类刻意节省心智的场景里。

六、PriorityQueue 和堆排序是什么关系

准确说法：PriorityQueue 的底层用二叉堆实现；堆排序是利用堆这个结构完成的排序算法。两者共享数据结构，但目标根本不同。

PriorityQueue 确实是个堆

  • OpenJDK 源码注释明确写着：内部表示为平衡二叉堆（binary heap），用数组存储。
  • 默认小顶堆，queue[0] 恒为最小值；传入 Comparator 可以改成大顶堆。
  • offer：插到数组末尾 + 上浮，**O(log n)**。
  • poll：取出堆顶，把末尾元素搬到堆顶 + 下沉，**O(log n)**。
  • 它没有维护整体顺序，迭代器的遍历顺序是无序的——这是最常被误判的一点。

关键区别

PriorityQueue 堆排序
身份 容器 / 数据结构 排序算法
适用场景 动态添加、随时取最值 对给定的静态数组就地排序
顺序保证 只保证队首最优，遍历无序 最终整体有序
空间 O(n) O(1) 原地
核心操作 offer / poll build-heap + 反复取堆顶下沉

一个类比：PriorityQueue 是一只”永远把最重要的文件压在最上面”的文件架，你可以随时往里塞、随时抽最上面那份；堆排序则是”一次性把一堆乱文件按重要性彻底整理好”的那个过程。文件架只管顶部，整理完的档案柜才保证全序。

所以不能说 PriorityQueue 就是堆排序，只能说它们同源。第三节里那段基于 PriorityQueue 的实现是合法用法，但它在空间复杂度上已经不是堆排序了。

七、小结

堆排序值得留下的不是那段代码，而是四条能横向迁移的认知：

  1. 一切公式都能从”完全二叉树的下标算术”推出来。 n/2 - 1、2i+1、(i-1)/2 都不需要背，用”叶子 ⇔ 没有左孩子 ⇔ 2i+1 ≥ n“当场反解即可。
  2. “从后往前”不是技巧而是前提。 siftDown 只能做局部决策，它依赖子树已经成堆——这个依赖关系决定了遍历方向。凡是分治式的自底向上调整，都要先问一句”我的孩子处理好了吗”。
  3. 复杂度的惊喜藏在求和里。 建堆 O(n) 而不是 O(n log n)，原因下沉距离与节点数呈指数级反向关系。看到”对每个节点做一次 O(log n) 操作”就断言总代价 O(n log n)，是算法分析里最常见的懒惰推理。
  4. 基（0 基 / 1 基）是一个契约，不是一行偏移。 起点、终止条件、size 的开闭区间必须成套替换；混用时最危险的是**”1 基写成 0 基起点”会静默漏掉一个节点**，而不是立刻抛异常。

顺带澄清一句常被混谈的关系：**PriorityQueue 提供了堆这个数据结构，堆排序提供了用它完成排序的算法**，二者同源而不同义。

记忆卡

建堆 n/2-1 起，从后往前保证子树成堆；大顶堆出升序，小顶堆出降序；0 基与 1 基的公式成套换，size 开闭区间要统一；PriorityQueue 是堆做的容器，不是堆排序。

自检清单

  • n = 1、2、3、8 四个边界各手写跑一遍，尤其确认 n=1 时循环是否自然跳过。
  • 0 基与 1 基各实现一遍，对比两者的 siftDown 判据（< 还是 <=）。
  • 数一下你的实现调整了几个节点，答案应该正好是 ⌊n/2⌋。
