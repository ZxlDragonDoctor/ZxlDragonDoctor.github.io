# 从"单据锁"到"用户想买两个"：一场后端面试的 8 道追问与幂等设计复盘

> 面试官真正考的不是你背了多少方案，而是你能不能**先分辨场景，再选手段**。
> 本文基于一次真实的 Java 后端 / AI Agent 方向面试复盘，保留简历 WMS 经历与原题原文，给出逐题答案与两个版本的对比修正。

## 写在前面

这场面试的追问链条很典型：从简历上的两段 ERP/WMS 经历出发，先问**单据锁、可用库存、任务调度**，再转到**乐观锁与幂等**，最后由** MQ 重复消费**层层追问到**用户重复下单**、**开源 PR 的事件去重**，最后落到跨境支付业务和 AI 应用。

复盘下来，最大的失分点不是"不会"，而是：**没先做场景定性，就直接答方案**。最典型的第 5 题——两道题都在考幂等，但一道是"同一条消息重复投递"，一道是"两次请求代表同一次意图"，去重凭证的来源完全不同，当时却用同一套思路回答了。

下面先放原始材料，再逐题给答案。

## 三、逐题解析

### 第 1 题：单据锁是什么？是行锁吗？

**单据锁是业务层的叫法，不是数据库概念**——指处理同一张单据时的互斥保护。在你的代码里，它就是**数据库行锁 + 外层任务锁两层**：

- `WmsUtils.getStockoutOrder(..., true, ...)` 的 `true` 分支执行 `SELECT ... FOR UPDATE`，锁住**这张出库单记录**，事务提交或回滚时释放。同一张单被两个事务同时分配，后来的会在此等待。
- 自动分配任务外层还有 `session.getLock(...)` 任务锁，防止批处理任务重叠运行。

**注意边界**：它只保护被锁的这一行，**不代表整张库存表都被锁住**。而且 `FOR UPDATE` 要命中索引才锁行，不走索引会升级成锁全表。

> **面试话术**："这里的单据锁主要是数据库行锁。`getStockoutOrder` 传 true 走 `SELECT ... FOR UPDATE` 锁住出库单这一行，事务结束释放，避免两个事务同时处理同一张单。它只保护这一行，不是锁整张库存表。外层还有任务锁防止批处理重叠，这是另一层。"

---

### 第 2 题：预占量是什么？可用库存存在哪？

**预占量**是已被订单或业务流程占住、暂时不能再分配给其他订单的库存，不代表已经实际出库。生命周期是：下单时加预占（实物不动）→ 出库时扣实物并释放预占 → 取消时只释放预占。

**可用库存要分两层讲**（这是一处关键修正，不能简单说"实时算、不存字段"）：

| 层级 | 实现 | 说明 |
|---|---|---|
| 货位明细层 | `StockSpecDetail.canUseStockNum()` = `stock_num - reserve_num` | 计算值，不是单独字段；按仓库/SKU/残次/货位/批次/效期的细粒度 |
| 汇总层 | `stock_available_num` 表，按仓库/SKU/残次/类型存 `num` | 类型区分正常库存与待质检库存；服务按 SKU 的可用库存和订单预占流程 |

> **面试话术**："预占量是已占住、还没实际出库的库存。分两层：明细层按 `stock_num - reserve_num` 算可用量；系统另有汇总表按 SKU 和库存类型存可用量，服务于订单预占。回答时我会先说明讲的是哪一层。"

---

### 第 3 题：为什么任务表 + RocketMQ？定时任务不行吗？

**先纠正表述**：不是 RocketMQ 去数据库取任务。调度端先从 `stock_sync_outer_order` 批量扫到期任务，再投递 MQ，消费者执行外仓查询。

| 组件 | 角色 |
|---|---|
| 任务表 | 保存任务状态、失败次数、下次执行时间 |
| 调度器 | 扫描到期任务并投递 |
| RocketMQ | 把调度与外部接口调用解耦，支持消费者并发和缓冲流量 |
| 定时任务/线程池 | 项目里也有直接用消费线程池处理的路径 |

**关键点**：流量小、系统简单时，"定时轮询 + 线程池"完全够用。上 MQ 是为了**解耦、削峰、独立扩缩容**，不是因为轮询不行。而且用了 MQ 后仍要按业务任务 ID 做幂等——消息会重投。

> **面试话术**："数据库表存任务状态，调度器扫到期任务投 MQ，消费者查外仓；成功删任务，失败更新状态和延迟时间重试。MQ 把调度和调用解耦，也便于并发和缓冲。简单场景线程池也够，上 MQ 取决于吞吐和解耦需求。用了 MQ 还要按业务任务 ID 做幂等。"

### 第 4 题：库存增减并发怎么保证正确？

**这是第二处关键修正：不要把简历的"乐观锁"和这份代码绑定。**

先看通用解法，分两种写法：

```sql
-- ① 简单加减：数据库原子更新，看影响行数判断成功/库存不足
UPDATE stock SET quantity = quantity + :delta
WHERE id = :id AND quantity + :delta >= 0;

-- ② 新值依赖旧状态：版本号 CAS，影响行数 0 则重读重算、有限重试
UPDATE stock SET quantity = :newQuantity, version = version + 1
WHERE id = :id AND version = :oldVersion;
```

第一种让数据库做原子加减，避免两个线程都基于旧值计算再覆盖（丢失更新）；第二种才是标准乐观锁。

**但结合真实代码要如实说**：出库单是明确的 `FOR UPDATE` 行锁；库存明细更新是重读后比较旧 `reserve_num`、变化就中断，批量更新前按 `rec_id` 排序降低死锁风险——**代码里没有 version 字段比较式更新**。

> **面试话术**："简单加减我用数据库原子更新，避免丢失更新；新值依赖旧状态时用版本号 CAS 加有限重试。但结合我的代码如实说：出库单是 `FOR UPDATE`，库存明细是旧值校验加 `rec_id` 排序防死锁，没有 version 字段，所以我不会把它说成版本号乐观锁。"

### 第 5 题⭐：两道幂等题为什么不是一回事

这是本次面试的核心失分点。**一句话记住**：

> **A 是技术层面的"同一条消息重复到达"，凭证是 MQ 给的；B 是业务层面的"两次请求代表同一意图"，凭证要业务自己造。**

| 维度 | A：MQ 重复投递 | B：用户连点下单 |
|---|---|---|
| 重复的是什么 | 同一条消息（msgId 相同、消息体相同） | 两次独立请求（msgId 不同） |
| 去重凭证 | 业务创建时生成的稳定 `eventId` | 结算单/草稿 ID 或复用的 `Idempotency-Key` |
| 处理位置 | 消费端 | 接口入口 |
| 手段 | inbox 唯一键 + 业务更新**同事务** | 唯一约束 + 保存首次结果，另一个请求返回同一订单 |
| 难点 | 去重记录与业务的原子性 | **凭证怎么造、怎么代表购买意图** |

**两个容易踩的坑**（代码版补充，很关键）：

1. 不要只依赖 Broker 临时生成的消息 ID；也不要用消息内容哈希——**两笔真实业务的内容可能完全相同，但都是合法操作**。
2. 按"用户 + 商品 + 几秒时间窗"去重也不安全，因为用户可能确实要连续买两笔相同商品。

> **面试模板**："MQ 重复投递是同一个事件再次消费，我用稳定事件 ID 做消费去重，去重记录和业务更新放在同一事务。用户连点即使请求 ID 不同，只要属于同一次提交就复用同一个业务幂等键，靠唯一约束只创建一次、返回首次结果。关键是先分清重复的是事件还是意图，再选凭证。"

### 第 5 题延伸："那用户就是想买两个呢？"

这是面试官最想听到的追问，很多人答到"唯一索引挡住重复"就停了。

**结论：不会误杀，前提是凭证绑定的是"一次购买意图"，而不是"用户+商品"或"一次点击"。**

| 场景 | 用户真实意图 | 凭证 | 系统行为 |
|---|---|---|---|
| 手抖连点 2 次 | 买 1 件 | 同一个 token/requestId | 第 2 次拦住 |
| 想买 2 件 | 买 2 件 | 一个结算页，数量改成 2 | 一张订单、数量=2 |
| 真的下 2 笔单（不同地址） | 两次独立购买 | 两个不同 requestId | 两笔订单都成功 |

**两个反面案例**：

- 幂等键用 `userId + skuId` → 用户想下第二单被误杀（粒度太粗）。
- 每次点击都生成新 requestId → 连点挡不住（粒度太细）。

**系统没法读心**，区分"手抖"和"真想再买"必须靠用户做一个明确动作表达新意图：第一次下单后 token 作废，想再买要**重新进结算页领新 token**；requestId 在结算页初始化时生成、本页内复用，想下第二单要重新走流程。

> **关键认知**：**幂等 ≠ 限购**。幂等保证"一次意图只生效一次"；"一个人能买几个"是业务规则（数量、库存、限购），两者不能混。若请求没有共同业务键或幂等令牌，服务端**无法可靠判断**两笔相同请求是重试还是新单——这是诚实但必须讲清的边界。

### 第 6 题：PI-Desktop PR #1499 怎么处理重复事件

**先定性**：这个 PR 处理的是 system transcript 事件在持久化和回放时重复，**不是订单或支付的重复提交**。

- **根因**：原来按对象引用（object identity）判重，事件被克隆或反序列化重建后引用变了，就被当成新事件追加，撑大模型 context。
- **改法**：将 system message 规范化序列化，身份包含**正文内容、工具声明、时间戳**；在持久化、恢复、记忆、回放路径统一用这个身份去重。
- **结果**：内容和时间戳都相同的克隆只保留一份；内容相同但时间戳不同的保留。回放折叠重复行，旧存储文件不立即重写。1303 个单测通过（E2E 因本机缺 Host Core/MSVC 链接器未跑，已在 PR 中如实标注）。

**和上一题的联系**：这里判重依据是**自己算的内容指纹**；下单幂等必须用**稳定业务键**。两笔真实订单内容可能完全相同，"内容+时间戳"身份不能直接拿来当订单幂等键。

### 第 7 题：跨境支付业务三问

#### A. 名字相近的公司怎么识别？（关键字匹配被否）

**方向性修正**：面试官否掉关键字匹配，**不是让你上大模型**，而是要**强标识匹配 + 独立来源核验**。

> "这是企业实体消歧。优先用注册国家/地区、注册号、税号这类强标识匹配；再规范化企业名和别名，从官方登记来源或合规数据服务取候选；对名称相近但标识不同的，模型帮助整理候选和解释匹配依据，但最终结合独立来源核验；证据冲突或置信度不足转人工。跨境支付还要关注受益所有人，FATF 客户尽职调查也要求用可靠独立来源核验身份。"

纯 LLM 语义判定可以作为辅助，但不能作为最终依据——金融场景要有可追溯的独立证据。

#### B. 多家收款接口怎么设计？

你答的策略模式方向对，但要补成组合拳：

- **策略**：每种收款方式一个实现；
- **适配器**：把各家 URL、参数、签名、响应差异封装起来，对上统一接口；
- **工厂/注册表**：按渠道配置选实现；
- **模板方法 + 公共编排**：固定创建/查询/退款/验签骨架，公共层负责订单状态、幂等、超时、日志，避免渠道差异散落。

> "统一渠道接口，每家一个策略加适配器，工厂按配置选实现，公共编排层负责状态、幂等、超时和日志；流程相同步骤不同就抽模板，参数差异用配置，协议和行为差异留在适配器。"

#### C. 用 AI 判断公司是否合法合规？

把"AI 自主判断"改成 **AI 辅助 KYB / 风险筛查**——不让模型凭网页信息直接下法律结论。

1. 先和合规团队明确适用地区、风险规则和审批边界；
2. 从可靠企业登记和合规数据源获取企业及受益所有人信息（**不让 AI 爬网页**，信息可能虚假、过时或被投毒）；
3. 分别做企业存续、制裁名单、受益所有人等检查；
4. AI 做资料抽取、名称归一、候选匹配、证据摘要；**规则引擎**按证据和阈值给出通过/拦截/待人工；
5. 结论保存来源、抓取时间、规则和模型版本、人工处置记录，并定期重筛。

制裁名单用 OFAC 官方提供的下载数据，而不是持续调用它的网页搜索工具（官方明确不建议自动化调用）。

### 第 8 题：用 Spring AI 做了什么？

**价值观修正：诚实 > 包装。**

你简历写了 Spring AI / RAG / Tool Calling / 多 Agent 编排，但实际只做了简单企业 AI 客服。如果包装成"RAG + Agent 系统"，面试官一追"向量库用什么？""接了哪些工具？""多 Agent 怎么编排？"——答不上就是减分甚至诚信风险。

## 四、两个版本的答案对比：通用话术 vs 真实代码

我把自己的通用版和另一份基于你真实代码的回答逐题做了比对，结论是**两份不是对错关系**：

| 版本 | 优势 | 风险 |
|---|---|---|
| 通用版（我） | 对照表、话术模板、三步框架、"想买两个"深度展开 | 3 处与实际代码不符 |
| 代码版 | 真实类名/方法名、纠正事实错误、官方标准引用、诚实原则 | 话术偏散 |

**六处必须记住的修正**：

1. **可用库存有两层**：明细层计算 + `stock_available_num` 汇总表，别说"不存字段"。
2. **乐观锁别绑定代码**：代码里是 `FOR UPDATE` + 旧值校验 + `rec_id` 排序，没有 version 字段。
3. **MQ 不取任务**：调度器扫表投递，消费者执行；线程池方案也成立，上 MQ 为解耦。
4. **单据锁是两层**：出库单行锁 + 外层任务锁，只锁这张单。
5. **幂等用稳定业务 ID**：不用 Broker 临时 ID、不用内容哈希；无共同键就无法判断重试 vs 新单。
6. **公司名识别靠强标识**：注册号/税号 + 独立核验，LLM 是辅助；合规判断是 KYB，不是 AI 拍板。

**融合原则**：用代码版的**事实**修正通用版的**表述**，用通用版的**结构**承载代码版的**事实**。

## 五、总结：三条面试方法论

**1. 先定性，再答方案。**
遇到任何"重复/幂等"题，先套三步框架：
```
第一步：重复的是什么？—— 同一条消息 / 两次请求同一意图 / 内存对象副本
第二步：去重凭证是什么、从哪来？—— MQ 给的 / 业务造的 / 自己算的
第三步：怎么保证判重与处理原子？—— 唯一索引 / SETNX+Lua / CAS / 同事务
```
你这次吃亏就吃在跳过了第一步。

**2. 项目和技能要能互相印证。**
简历写了 Spring AI / RAG / 多 Agent，第 8 题却答"简单客服"，面试官会怀疑深度。做过什么讲什么，没做过的说"了解方向、准备怎么落地"，把追问变成展示学习能力的机会。

**3. 诚实比漂亮话更稳。**
"简历的乐观锁和代码不是一回事"就如实区分机制；E2E 没跑就标注未验证；PR 里如实写限制。面试官追问的是细节，编造的细节经不起第二问。
