## 多个`<table>`标签

多个`<table>`标签并非冗余，而是基于 **“模板分离、状态切换、功能分工”** 的设计思路，分别承担“数据渲染模板”“新增行模板”“视图模式适配”三大核心角色。每个表格的作用和关联逻辑如下，可按“模板类型”分类理解：


### 一、核心功能表格：`#count_apply_detail`（主数据展示表格）
这是 **唯一用于“实时展示和编辑计数单明细数据”的核心表格**，也是用户直接交互的表格（如查看货品信息、修改采购量）。

#### 关键属性与作用：
- **`row_template="#count_apply_detail_temp > tr"`**：指定“已存在数据行”的渲染模板（关联`#count_apply_detail_temp`表格的`<tr>`），即加载历史数据时，用这个模板生成每行内容。
- **`relative_row_template="#count_apply_detail_new > tr"`**：指定“新增数据行”的渲染模板（关联`#count_apply_detail_new`表格的`<tr>`），即点击“添加单品”时，用这个模板生成新的可编辑行。
- **`.listview`/`fixedrows="1"`/`fixedlayout`**：框架样式/功能类，确保表格是“列表视图”、固定表头（第一行为表头不滚动）、固定列宽布局，提升交互体验。
- **`<tr .header>`**：定义表头（商家编码、货品编号等），仅用于展示列名，不参与数据渲染。

#### 总结：
它是“数据容器”，本身不存储模板结构，而是通过`row_template`和`relative_row_template`关联其他模板表格，动态生成数据行。


### 二、模板表格1：`#count_apply_detail_temp`（已存在数据行模板）
这是 **“加载历史数据时的行模板”**，用于渲染从数据库查询到的已有明细（如编辑已有计数单时，展示已添加的货品）。

#### 关键设计与作用：
- **`.temp`类**：框架约定的“模板类”，通常在CSS中配置为`display: none`，仅作为模板被引用，不直接在页面显示。
- **`<tr>`内的`<td>`配置**：
  - `field="spec_no"`/`field="goods_no"`：绑定数据字段，即渲染时从后台数据中取`spec_no`（商家编码）、`goods_no`（货品编号）等字段值，填充到对应单元格。
  - `.readonly`：标记该单元格“只读不可编辑”（如商家编码、货品编号是基础信息，不允许修改）。
  - `not_insert`：（框架自定义属性）可能表示“新增行时不显示该字段”或“该字段不参与新增数据的提交”，仅用于展示已有数据。
  - `field="num"`+`filter=".0~9"`+`v_require`：采购量字段，允许编辑（无`.readonly`），限制输入为数字，且为必填项（`v_require`）。

#### 总结：
针对“已有数据”的渲染需求，强调“部分字段只读、采购量可编辑”，适配“编辑历史明细”的场景。


### 三、模板表格2：`#count_apply_detail_new`（新增数据行模板）
这是 **“点击‘添加单品’时生成新行的模板”**，用于用户新增货品明细（如创建新计数单时，添加需要计数的货品）。

#### 与`#count_apply_detail_temp`的核心差异：
1. **`<tr edit changed>`**：
   - `edit`：标记这是“可编辑行”，框架可能会为该行添加编辑态样式（如边框高亮）。
   - `changed`：（框架自定义属性）标记该行“已修改”，用于后续提交时识别哪些新增行需要保存到数据库。
2. **`not_bind`属性**：
   - 如`field="num" not_bind`/`edit field="remark" not_bind`：表示“新增时该字段不与后台初始数据绑定”（因为新增行本身没有后台数据），仅作为用户输入的临时容器，提交时再将值传给后台。
3. **字段权限一致**：
   - 与`#count_apply_detail_temp`一样，基础信息（商家编码、货品编号等）仍为`.readonly`（新增时可能通过“选择单品”自动填充，不允许手动输入），仅采购量和备注可编辑。

#### 总结：
针对“新增数据”的交互需求，强调“行编辑态标记、临时输入不绑定初始数据”，适配“添加新货品”的场景。


### 四、视图切换表格：`#count_apply_detail_view` + `#count_apply_detail_temp_view`（只读视图模板）
这两组表格是 **“只读视图”的专用模板**，用于“非编辑场景”（如查看已提交/已审核的计数单，不允许修改数据），通过`body[show_mode]`状态控制显示/隐藏。

#### 关键逻辑：
1. **状态控制（CSS部分）**：
   ```css
   /* 当body的show_mode为"view"（只读视图）时：
      - 隐藏可编辑的#count_apply_detail表格
      - 显示只读的#count_apply_detail_view表格 */
   body[show_mode="view"] #count_apply_detail { display: none; }
   body[show_mode="view"] #count_apply_detail_view { display: block; }
   ```
   - 其他状态（如`edit_view`编辑态、`submit_view`提交后视图）则隐藏`#count_apply_detail_view`，显示可编辑的`#count_apply_detail`。

2. **`#count_apply_detail_view`与`#count_apply_detail`的差异**：
   - 无`relative_row_template`：只读视图不需要“新增行”，因此不关联新增模板。
   - 初始为`.temp`（隐藏）：仅在`show_mode="view"`时才显示。

3. **`#count_apply_detail_temp_view`（只读行模板）**：
   - 无`.readonly`标记，但因为整个表格在只读视图下显示，且无`edit`态配置，实际效果为“全行列只读”。
   - 无`not_insert`/`not_bind`等交互属性：仅用于纯展示，不涉及编辑或提交。

#### 总结：
针对“只读场景”的展示需求，通过状态切换隐藏编辑功能，仅保留数据展示，适配“查看已完成计数单”的场景。


### 五、所有表格的关联逻辑（一句话总结）
| 表格ID                          | 类型         | 核心作用                             | 显示时机                                        |
| ------------------------------- | ------------ | ------------------------------------ | ----------------------------------------------- |
| `#count_apply_detail`           | 核心数据容器 | 展示/编辑明细数据，关联其他模板      | 编辑态（`edit_view`）、提交后态                 |
| `#count_apply_detail_temp`      | 已有数据模板 | 渲染历史明细行，部分字段只读         | 加载已有数据时（通过`row_template`）            |
| `#count_apply_detail_new`       | 新增数据模板 | 生成新增明细行，标记编辑态和临时输入 | 点击“添加单品”时（通过`relative_row_template`） |
| `#count_apply_detail_view`      | 只读数据容器 | 展示只读明细数据，无编辑功能         | 只读态（`show_mode="view"`）                    |
| `#count_apply_detail_temp_view` | 只读行模板   | 渲染只读明细行，全行列不可编辑       | 只读态（通过`row_template`）                    |


### 六、设计思路的优势
1. **职责分离**：将“容器”“已有数据模板”“新增数据模板”“只读模板”分开，避免单个表格内逻辑混乱，便于维护（如修改新增行样式只需改`#count_apply_detail_new`）。
2. **状态适配**：通过`show_mode`和模板切换，实现“编辑/新增/只读”多场景的无缝适配，无需动态修改单个表格的属性（如添加/移除`.readonly`）。
3. **框架兼容**：这类模板分离的设计，通常是适配Htmlayout等桌面端HTML框架的最佳实践，框架可通过`row_template`等属性高效渲染数据，减少DOM操作开销。

简单来说：**不是“多个表格重复”，而是“一个核心容器+多个场景化模板”，共同实现计数单明细的完整交互流程**。
